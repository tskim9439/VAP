# q06-s3-ast 한 스트림 실시간성(RTF) — mxc 호스트 예비 측정 (2026-10-12 14:16–14:53)

## 방법 (`experiments/stream_rtf.py`)
- 모델·입력·디코드: q06-s3-ast/final. 평가와 같은 입력(원 발화 + 꼬리 무음 1 s)·prefix(번역 모드, δ4·δ10)·직렬 디코드(`stream_decode`)를 쓴다. batch 1, fp32
- 문장: FLEURS 4 방향에서 길이 순으로 고르게 24 개씩(96 문장 × δ 2 개)
- 계산 시간:
  - 80 ms 디코더 step 마다 `stream_decode` 가 `torch.cuda.synchronize()` 후 잰 값
  - 인코더는 두 가지로 쟀다:
    - 파일 전체를 한 번에 인코딩한 시간을 청크 수로 나눈 하한(캐시 재사용 스트리밍에 가깝다)
    - 청크마다 4.8 s 창(왼쪽 문맥 56 + 청크 4 프레임)을 다시 인코딩한 상한: 중앙 29.6 ms, p95 35.6 ms
- 실시간 조건: 인코더가 320 ms(4 프레임) 청크 단위라, 청크 하나(인코더 + 디코더 4 step)를 320 ms 안에 끝내야 밀리지 않는다.
- 계산 시간 포함 LAAL(ca): 청크가 다 들어온 뒤 대기열로 처리한다고 보고 단어 시각을 다시 계산했다(lo = 인코더 하한, hi = 상한).
- 환경: 호스트 GPU 5(H200, 다른 작업 없음)
  - 호스트 CPU 부하가 매우 컸다(load average 200~330 / 96 코어).
  - 측정 중 GPU 사용률은 약 18 % 였다.
  - 처음 띄운 GPU 0 에는 측정 직전 다른 사용자 작업(85 GB)이 올라와, 측정 전에 GPU 5 로 옮겼다.

- 이 조건에서는 실시간을 못 맞춘다.
  - RTF 0.86~1.05 이고, 청크의 11~27 % 가 320 ms 를 넘는다.
  - 밀림이 쌓여 계산 시간 포함 LAAL 이 계산 시간 제외(enc)보다 0.5~1.3 s 크다.
- 인코더는 병목이 아니다. 캐시 없이 청크마다 4.8 s 를 다시 인코딩해도 30 ms 다.
- 디코더 step 의 중앙값 55 ms 는 thinker forward 두 번(오디오 위치 + `<NEXT_AUDIO>`)이다. forward 하나가 약 27 ms 다.
- 같은 호스트에서 bf16 은 오히려 느렸다(첫 21 문장 RTF 0.95~1.12).
  - GPU 사용률이 낮은 것과 함께 보면, 시간이 GPU 계산이 아니라 CPU 쪽(Python 디코드 루프·커널 실행)에서 든다.
  - 따라서 이 값은 부하 큰 공유 호스트 + 최적화하지 않은 HF eager 디코드의 상한으로 본다.
- 표본 24 문장의 LAAL(eval)은 전체 평가값과 조금 다르다(표본 차이). 영→한 δ4 처럼 enc 가 eval 보다 작은 경우가 있다. 늦어진 단어가 원 발화 끝을 넘으면 LAAL 의 합산 구간(τ)이 줄기 때문이다.
